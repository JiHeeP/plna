# PLNA 배포 검토 보고서

## Context

PLNA는 현재 **개인용 목표 관리 앱**으로, 특정 사용자 1명을 위해 만들어진 상태다.
**소수 지인에게 공유**하기 위해 배포하려 하며, 코드에 박혀 있는 개인 데이터와 구조적 한계를 먼저 파악해야 한다.

**배포 대상:** 소수 지인 (불특정 다수 SaaS가 아님)

---

## 1. 사용자가 바꿔야 하는데 이미 기입력된 사항

> "다른 사람이 이 앱을 받으면, 남의 목표가 내 앱에 떠 있는 상황"

### 1-1. 개인 목표가 코드에 하드코딩됨 (가장 심각)

| 위치 | 내용 | 문제 |

| `components/goals/big-three-cards.tsx:18-19` | `"1등급"`, `"연구대회 입상"` | 특정인의 커리어 목표 |
| `components/goals/big-three-cards.tsx:27-28` | `"60개"`, `"만능대화소재"` | 특정인의 대화 소재 목표 |
| `components/goals/big-three-cards.tsx:36-37` | `"100만원"`, `"강의 수익"` | 특정인의 수익 목표 |

**새 사용자 입장:** 앱을 열면 "연구대회 입상", "강의 수익 100만원"이라는 남의 목표가 보인다.

### 1-2. 기본 습관 7개가 특정인 맞춤

**파일:** `lib/constants.ts:19-27`

| 습관 | 문제 |
|------|------|
| `"기상 6시"` | 기상 시간은 사람마다 다름 |
| `"연구대회 2시간"` | 연구대회 참가자만 해당 |
| `"코딩/AI 다루기"` | 개발자/AI 관심자만 해당 |

`"운동 30분"`, `"명상 5분"`, `"책 읽기"`는 범용적이라 괜찮음.

### 1-3. 확언(Affirmation) 7개

**파일:** `lib/constants.ts:29-37`

내용 자체는 범용적인 한국어 확언이라 **큰 문제는 아님**. 다만 사용자가 자기 확언을 쓸 수 없고 7개로 고정됨.

### 1-4. 연도 2026 하드코딩

| 위치 | 내용 |
|------|------|
| `lib/constants.ts:39` | `YEAR_START = new Date(2026, 0, 1)` |

### 1-5. 축(Pillar) 이름

**파일:** `lib/constants.ts:1-5`

- `"나다운 나"` — 개인 철학적 표현. 범용적이지 않음
- `"일 (커리어)"`, `"자산"` — 비교적 범용적

## 2. 배포를 위한 개선 방향

### 2-1. 인증(Auth) 시스템: 현재 없음

**현재 상태:**
- 로그인/회원가입 없음
- 모든 API 라우트에 `user_id` 필터 없음
- DB 테이블에 `user_id` 컬럼 없음
- RLS(Row Level Security) 미적용
- middleware.ts 없음

**결과:** 앱을 배포하면 모든 사용자가 같은 데이터를 보고 수정함.

**개선 방향 (소수 지인 대상):**

소수 지인이라도 각자의 데이터가 분리되어야 하므로 인증은 필요하지만, 가벼운 방식으로 가능:

- **Supabase Auth** (이메일 로그인 또는 매직 링크) — 복잡한 소셜 로그인 불필요
- 모든 테이블에 `user_id` 컬럼 추가 + RLS 정책 설정
- 모든 API 라우트에 인증 확인 + user_id 필터 추가
- auth middleware 추가
- (선택) 초대 코드로 가입 제한 — 아는 사람만 가입 가능

### 2-2. 하드코딩된 개인 데이터 → DB/설정으로 이동

| 항목 | 현재 | 개선 방향 |
|------|------|-----------|
| Big Three 목표 | 코드에 하드코딩 | DB의 사용자 설정 테이블로 이동, 온보딩 시 입력 |
| 기본 습관 | `constants.ts`에 7개 고정 | 범용 기본값 제공 + 사용자 커스터마이징 UI |
| 확언 | `constants.ts`에 7개 고정 | 기본 제공 + 사용자 추가/수정 가능하게 |
| 축(Pillar) 이름 | `constants.ts`에 고정 | 기본값은 유지하되 사용자 변경 가능하게 |
| 연도 | 2026 하드코딩 | `new Date().getFullYear()` 동적 계산 |

### 2-3. 온보딩 플로우 필요

현재는 앱을 열면 바로 대시보드가 나옴. 새 사용자를 위해:
1. 회원가입/로그인
2. 3대 축 이름 설정 (기본값 제공)
3. Big Three 목표 입력 (label, subtitle, target 수치)
4. 기본 습관 선택/커스터마이징
5. 대시보드로 이동

소수 지인 대상이므로 복잡한 위저드 대신 **첫 로그인 시 기본값 자동 생성** 후 설정에서 수정하는 방식도 충분.

### 2-4. 개인 파일 제거

| 파일 | 조치 |
|------|------|
| `ops/logs/2026-03-07-discord-night-log.md` | **삭제** — 개인 일과/수업 준비 내용 포함 |
| `GUIDE_MAIN_APP.md` | 개인 슬로건 "1-60-100" 제거 또는 범용화 |

### 2-5. PWA 메타데이터 범용화

`public/manifest.json`의 `name`과 `description`에서 "2026"과 "1-60-100" 제거.

## 3. 새 repo를 만들어야 하는가?

### 결론: 새 repo를 만드는 것을 권장

### 이유

| 관점 | 현재 repo 유지 | 새 repo 생성 |
|------|---------------|-------------|
| **커밋 히스토리** | 개인 목표/습관 관련 커밋 메시지가 남아 있음 | 깨끗한 시작 |
| **ops/logs** | 개인 일과 기록이 git history에 남음 (파일 삭제해도 history에 존재) | 포함되지 않음 |
| **GUIDE 문서** | 개인 컨텍스트("1-60-100") 흔적 | 범용 문서로 새로 작성 |
| **브랜치 관리** | 개인 개발 브랜치들이 혼재 | 배포용으로 깔끔하게 관리 |
| **목적 분리** | 개인용 + 배포용 혼재 → 관리 복잡 | 개인용/배포용 명확히 분리 |

### 단, 현재 repo를 유지해도 되는 경우

- `.gitignore`가 잘 설정되어 있고 시크릿 유출 없음
- `scripts/check-secrets.mjs`로 시크릿 검증 가능
- 커밋 히스토리에 API 키 등 민감 정보 없음 (확인 완료)

**현재 repo를 유지하면서 배포하려면** `git filter-branch` 또는 `git filter-repo`로 개인 로그 파일의 히스토리를 제거해야 하는데, 이는 새 repo를 만드는 것보다 복잡함.

### 권장 방식

```
현재 repo (plna)          →  개인 개발/실험용으로 유지
새 repo (plna-public 등)  →  배포용, 범용화된 코드만 포함
```

1. 현재 코드에서 개인 데이터 제거 + 범용화 작업 완료
2. 새 repo에 깨끗한 상태로 push
3. 이후 기능 개발은 새 repo에서 진행

## 자체 검토

### 우선순위가 맞는가?
- **맞음.** Auth 없이 배포하면 데이터가 공유되므로, 인증이 최우선. 하드코딩 제거는 그다음.

### 빠뜨린 것은 없는가?
- Samsung Notes 임포트(`samsung-notes-import.tsx`) — 특정 기기 사용자용이지만, 선택적 기능이므로 있어도 무방
- X(Twitter) 연동 — API 키가 env로 분리되어 있으므로 구조적 문제 없음
- Kimi AI 연동 — 규칙 기반 폴백이 있어 API 키 없어도 동작함. 문제 없음

### 작업 범위가 과하지 않은가?
- 소수 지인 대상이라도 각자 데이터 분리는 필수 → Auth + user_id + RLS는 필요
- 단, 온보딩은 간소화 가능 (복잡한 위저드 대신 첫 로그인 시 기본값 자동 생성)
- 소셜 로그인, 결제, 관리자 패널 등은 불필요

### 새 repo 권장이 맞는가?
- **맞음.** `ops/logs`의 개인 기록이 git history에 남아 있고, filter-branch는 리스크가 큼. 새 repo가 가장 깔끔함.

## 구현 순서 (소수 지인 배포)

| 순서 | 작업 | 설명 |
|------|------|------|
| 1 | 하드코딩 제거 | Big Three, 습관, 연도, 슬로건 범용화 |
| 2 | Supabase Auth 도입 | 이메일/매직 링크 로그인 + middleware |
| 3 | DB 스키마 변경 | 모든 테이블에 `user_id` + RLS |
| 4 | API 라우트 수정 | 인증 확인 + user_id 필터 |
| 5 | 간소 온보딩 | 첫 로그인 시 기본 습관/설정 자동 생성 |
| 6 | 개인 파일 정리 | ops/logs 삭제, 문서 범용화 |
| 7 | 새 repo 생성 | 깨끗한 코드만 push |
| 8 | 배포 | Vercel로 배포 + 지인에게 링크 공유 |
